# Архитектура и технические решения

## Базовый стек

Новый проект: frontend React + TypeScript + Vite; backend Python + FastAPI; PostgreSQL с pgvector; отдельный worker для экспорта и индексации; SQLAlchemy и Alembic для БД и миграций. Файлы хранятся за серверной авторизацией, с возможностью S3-совместимого хранилища в production. Сессионная авторизация через cookie; запросы браузера идут через один origin или корректно настроенный reverse proxy.

Компонентные примитивы можно использовать, но внешний вид определяет DESIGN_SPEC.md. Не подменять выбранный дизайн стандартной темой UI-библиотеки. Версии зависимостей закрепить lock-файлами после проверки актуальной официальной документации. Не устанавливать случайные библиотеки ради одной функции.

Эквивалентный стек допустим в существующем репозитории, если сохраняет серверные возможности, миграции, worker, надежное хранение и критерии приемки. Не переносить секреты и обход прав в браузер ради упрощения.

## Структура репозитория

```text
apps/web/                 публичный и административный интерфейс
apps/api/                 HTTP API, auth, chat, FAQ, usage
apps/worker/              экспорт, импорт знаний, очистка
db/migrations/            Alembic
knowledge/sources/        исходники версий без публичной раздачи
assets/mascot/            согласованные ассеты состояний
tests/unit/               правила экспорта, тарификация, валидация
tests/integration/        БД, права, идемпотентность, публикация
tests/e2e/                основные браузерные сценарии
evals/                    утвержденные вопросы и результаты модели
docs/                     запуск, эксплуатация, результаты приемки
docker-compose.yml        локальные сервисы
.env.example              имена настроек без секретов
```

Не использовать файл JSON или localStorage как единственное хранилище истории. localStorage допустим только для некритичных предпочтений интерфейса. Не помещать session_token, API-ключи и пароль в localStorage.

## Запрос чата

1. Проверить сессию, принадлежность беседы, длину, идемпотентность, лимиты и отсутствие активного запроса.
2. Транзакционно сохранить question и chat_request; вернуть 202 с request_id. Фронтенд опрашивает статус или использует серверные события статуса без непроверенного текста.
3. Выбрать опубликованную версию базы. Построить поисковый запрос с учетом предыдущего вопроса, без раскрытия чужого контекста.
4. Провести полнотекстовый и семантический поиск с фильтром сезона и статуса. Короткие структурированные FAQ сохранять целиком, не теряя исключений. Если нужны несколько связанных фрагментов, добавить их по parent_id.
5. При недостаточной информации выбрать clarification или no_answer. Нельзя заполнять отсутствующие сведения из памяти модели.
6. Вызвать GPT с системной инструкцией и ограниченным контекстом. Проверить JSON-схему и IDs источников; для критических чисел и условий сверить опору на источники. Семантический verifier допускается как дополнительный измеряемый вызов, который тоже учитывается.
7. Сохранить usage каждой попытки даже при непригодном ответе. В одной транзакции завершить запрос и создать одно итоговое сообщение помощника. При нарушении структуры — безопасный отказ, не сырой JSON пользователю.
8. Освободить или скорректировать бюджетный резерв. Передать завершенный результат интерфейсу. Разрыв соединения браузера не должен автоматически отменять сохранение результата.

Полная гарантия безошибочности модели невозможна; контролируются источники, тема, критические факты и контрольный набор. Проверку существования source_id нельзя выдавать за проверку всей семантики ответа.

## GPT

Стартовая модель `gpt-6-luna`, Responses API. Начальная настройка `reasoning.effort=low`; сравнить с `none` на контрольном наборе. Для low не копировать temperature из старого кода. Максимум выходных токенов 1 600 включает reasoning. Видимый ответ краткий; если лимит нарушил завершенность результата, не публиковать обрезанный ответ как полноценный.

Рабочий бюджет входа 8 000 токенов, включая инструкции, 4–8 фрагментов и 6–10 последних реплик. Это отправные параметры, проверяемые на длинных вопросах. Если контекст слишком велик, уменьшать объем или извлекать нужные условия; не отбрасывать молча сам вопрос и существенные ограничения.

Structured output задает поля `status`, `answer`, `source_ids`, `follow_up`. Статусы: answered, clarification, no_answer, off_topic. Сервер вычисляет технические состояния error/rate_limited/budget_exceeded самостоятельно. Идентификаторы берутся из серверного списка найденных фрагментов. Модель не получает доступ к экспорту, SQL и секретам.

В сравнительные испытания включить `gpt-6.1-sol` на тех же вопросах. Замена основной модели допустима по отчету: доля корректных ответов, ошибки по условиям и срокам, p95 задержки, фактическая стоимость. Не подключать более дорогую модель автоматически, если в базе нет ответа. Доступность проверяется в аккаунте заказчика; платные тесты в рамках подготовки этого пакета не выполнялись.

Для embeddings выбрать доступную мультиязычную модель по тестам поиска, записать ее ID, размерность и версию индекса. При смене embeddings выполнить полную переиндексацию в отдельной версии. Не смешивать в одном индексе несовместимые векторы.

## Тарифы и бюджет

На дату проверки 20.10.2026 ставки Standard / short context для gpt-6-luna: input $0.10, cached read $0.01, cache write $0.125, output $0.50 за 1 млн токенов. Для gpt-6.1-sol: $2 / $0.10 / $2.50 / $10. Перепроверить перед запуском и сохранить pricing_version. Источник — официальные модели и Pricing из SOURCES.md.

Расчет: uncached_input = input_total − cached_read − cache_write, если именно такую семантику сообщает текущий API. Проверить неотрицательность и инварианты на реальном usage. Каждая непересекающаяся категория умножается на свой тариф. Reasoning не прибавляется повторно к output. Неизвестная категория не получает нулевую стоимость без основания; ставится unknown/partial.

Пример при 3 000 обычных input и 400 суммарных output: Luna $0.0005 за один модельный вызов, $5 за 10 000. Это пример арифметики, а не прогноз расходов сервиса. В стоимость вопроса входят дополнительные проверки, попытки, поиск; в общую эксплуатацию — импорт и хостинг.

Перед вызовом в транзакции резервировать верхнюю оценку расхода, учитывая output cap, тарифный режим и незавершенные запросы. Резервы и лимиты в валюте API, точные decimal, не binary float. Дневные и месячные окна — Europe/Moscow; деньги хранятся с валютой. Unknown-usage сохраняет резерв до сверки по регламенту.

## Экспорты

Фиксировать snapshot watermark через монотонный message sequence либо транзакционную snapshot-механику. Одного `created_at <= now` недостаточно, если сообщение может быть записано позднее со старым временем. Брать серверное время, не время клиента. Для N выбирать newest, затем сериализовать oldest-first.

Worker читает данные пакетами. Не держать весь массив 100 000 сообщений в памяти. Выборка детерминирована. Готовый файл проверяется на количество и доступность до статуса ready. Повтор worker-job не создает дубли экспортов и не меняет зафиксированный срез.

## Безопасность и наблюдаемость

Хеш пароля через поддерживаемую библиотеку; httpOnly, Secure в production, SameSite cookie; CSRF для state-changing действий. Проверять права на каждом endpoint. Лимит входа по источнику и учетной записи, защита от массового подбора без вечной блокировки владельца. Пароль production не имеет значения по умолчанию.

Структурированные логи с request_id, без ключей и полных тел частных диалогов. Метрики ошибок, задержки, очереди, unknown usage, стоимости и последней успешной резервной копии. Ошибки в пользовательском интерфейсе содержат безопасное сообщение и trace_id.

Ограничить URL источников: не выполнять запросы по ссылкам пользователя, не подгружать произвольные внутренние URL при импорте. HTML и Markdown очищаются. Срок жизни экспорта, удаление сообщений и ротация копий выполняются worker-задачами. После восстановления повторно применяются зарегистрированные удаления.
