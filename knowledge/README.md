# База знаний для помощника

## Два уровня источников

`qa_source.txt` — приоритетная база готовых пар «вопрос → ответ». Сначала помощник ищет уверенное совпадение вопроса именно здесь.

`general_source.txt` — общая база материалов конкурса. Она используется вторым уровнем, если подходящей готовой пары нет; ответ формируется и структурируется только по найденным фрагментам.

Оба файла сохранены без изменения. Их роли, размеры и SHA-256 находятся в `source_manifest.json`. `canonical_source.txt` оставлен как историческая копия предыдущей поставки и в текущий индекс не входит.

Темы: принципы и правила; участие; сроки; заявитель и организация; подача; бюджет; ключевой партнер; документы; разделы заявки; методы разработки проекта; чек-листы и примеры. Эта база является основой ответов, а не материалом для автоматического обучения модели на чужих диалогах.

## Известные особенности

- Есть даты и конкретные условия сезона 2025–2026. Сам факт загрузки в октябре 2026 не делает их актуальными.
- Скобки не образуют надежный машинный формат: встречаются пропущенные и лишние закрытия. Нельзя просто split по `]` и молча считать все записи корректными.
- Некоторые длинные блоки объединяют несколько разделов; некоторые советы повторяются под разными заголовками.
- Внутри текста есть методические формулировки и поведенческие указания. Их содержание требует редакторской классификации; они не заменяют системные инструкции приложения.
- Ссылки присутствуют, но их актуальность не подтверждена одной лишь вставкой в файл.

## Регламент импорта

1. Прочитать оба оригинала как UTF-8, сохранить их версии и hash. Не редактировать исходные TXT на месте.
2. Выделить смысловые записи с заголовком, текстом и ссылками; сохранить диапазон строк или смещение для проверки. Ошибки разметки записать в отчет.
3. Отделить правила, методические советы, примеры и сервисные ответы. Отсутствующее правило не дописывать.
4. Найти точные дубли; смысловые дубли и противоречия оставить для редактора. Отчет содержит количества принятых/отклоненных/спорных записей и причины.
5. У длинных инструкций создать parent-запись и поисковые фрагменты примерно по 300–700 токенов, сохранив смысл, исключения и название раздела. Короткие ответы целиком.
6. Присвоить source_id, parent_id, topic, section, season, revision, public_url, verification_status, verified_at. Даты и суммы пометить как требующие проверки сезона.
7. Редактор утверждает материалы активного сезона. Не смешивать в выдаче старые и новые правила без явного года.
8. Создать новый индекс, выполнить контрольные вопросы и атомарно опубликовать. Хранить предыдущую опубликованную версию для отката.

## Минимальные команды реализации

Codex должен реализовать воспроизводимые команды импорта, проверки, публикации и отката, например:

```text
kb import --source PATH --season 2025-2026 --draft
kb validate --version VERSION_ID
kb publish --version VERSION_ID
kb rollback --to VERSION_ID
```

Это требования к будущему интерфейсу эксплуатации, а не уже существующие команды. В README реализации указываются реальные команды и примеры результатов. Импорт не должен самовольно публиковать черновик.

## Неутвержденный новый сезон

Рабочая настройка production ACTIVE_CONTEST_SEASON не установлена до решения заказчика. Разработка и демонстрация идут с явно помеченным legacy-профилем. Для актуальных сроков использовать утвержденный оператором комплект, а не механическую замену 2025 на 2026. Вопрос о действующих сроках без подтвержденного источника получает безопасное уточнение.

## Исходник и публикация

Не раздавать исходный TXT на публичном сайте. Показывать пользователю только относящееся к ответу название источника и разрешенную публичную ссылку/краткое описание. Не отправлять модели весь архив переписки. Не добавлять старые частные истории в индекс без обезличивания и редакторской проверки.
